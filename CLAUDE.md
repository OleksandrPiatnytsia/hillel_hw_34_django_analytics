# Analytics service (ProjectB of the Hillel final homework)

Context for Claude Code sessions in this repository. Talk to the user in Ukrainian.

## What this is

The final Hillel Python Pro homework is two Django projects that talk to each other:

- **ProjectA = the bookstore**, an existing repository:
  `../hillel_hw_33_django_ci_cd_deploy` (GitHub OleksandrPiatnytsia/hillel_hw_33_django_ci_cd_deploy,
  deployed on Railway). The changes A needs for the final project (outbox, RabbitMQ publisher,
  analytics page, backfill API) are made **in that repository, in its own sessions**.
- **ProjectB = Analytics**, this repository (hillel_hw_34_django_analytics). Starts empty:
  README, .gitignore, MIT LICENSE, a `.venv` with Python 3.13 and no packages yet.

Mandatory for both projects (task text):
- Django + Django REST Framework, PostgreSQL, Redis, Celery, Docker Compose, NGINX, Gunicorn;
- custom user model, groups and permissions, class-based views with inheritance, JWT,
  Celery tasks, internationalization (2+ languages: uk, en), cache, Bootstrap UI;
- communication between the services via API, with error handling and logging;
- tests >= 70% coverage (unit, integration, API);
- Docker Compose with all services, CI/CD, production deploy, Sentry;
- README with an architecture diagram, run instructions, Swagger.

Agreed with the user: **no SPA** (the optional React/Vue part is skipped). Analytics is allowed
a smaller scope than the bookstore, but every mandatory element must be present.

## Architecture (approved 2026-11-17/18)

```
Bookstore (A)                                   Analytics (B)
 order saved ─> OutboxEvent row (same            consumer service (kombu)
               transaction)                       ├─ Event journal (event_id unique = idempotent)
 Celery task ─> RabbitMQ topic exchange           ├─ upsert Book / Category / Order / OrderLine
               "bookstore.events"  ───────────>   └─ manual ack AFTER the database commit
               publisher confirms                 queue "analytics.events" (durable)
                                                  dead-letter queue "analytics.events.dead"
 analytics page for managers  <──── REST ─────   /api/reports/* (JWT, Swagger)
 /api/orders/ (backfill source) ──── REST ────>  backfill management command
```

- **Events go ONLY through RabbitMQ.** The user explicitly rejected a REST fallback for events:
  reliability = outbox in A + publisher confirms + durable queue + manual ack + dead-letter queue
  + idempotent `event_id`.
- **REST stays for**: reports that A shows on its managers' analytics page (A calls B with a
  JWT of a service account, Redis cache, graceful message when B is down), and the backfill
  (B pulls old orders from A's API once).
- Celery broker stays **Redis** in both projects; RabbitMQ is only for the events.
- The shop must keep working when Analytics is down (events wait in the outbox / queue).
- Three events for the start: `order.created`, `order.paid`, `order.cancelled`.
  Each carries `event_id` (UUID), `type`, `occurred_at`, and an order snapshot (see below).
- **No personal data in Analytics**: no names, emails, phones, addresses. A customer is
  `customer_key` = a hash of A's user id (new vs returning customers still countable).
- Amounts: A converts to UAH itself (it knows its NBU rate) and sends ready UAH amounts.

Two repositories (the user decided against a monorepo):
- RabbitMQ lives in A's `docker-compose.yml` (A is the producer and must run without B).
  B's compose joins A's Docker network as an external network. Confirmed by the user 2026-11-18.
- B has its own PostgreSQL and its own Redis in its compose (confirmed 2026-11-18).
- Each repository has its own GitHub Actions CI. Railway: B and RabbitMQ go into the same
  Railway project as A (internal network); check the RabbitMQ cost first.
- Each README links the other repository and shows the shared architecture diagram.

## Analytics design (approved 2026-11-18)

Django apps and tables:
- `users`: custom `User`; groups `Analysts` (dashboard + reports) and `Services` (A's service
  account for the REST reports via JWT).
- `events`: `Event` (event_id UUID unique, type, occurred_at, received_at, payload JSON,
  status processed/failed, error, processed_at). Audit + the facts can be rebuilt from it.
- `catalog`: `Book` (source_id = A's id, title, author, publisher, language; upserted from
  event snapshots), `Category` + many-to-many with Book.
- `sales`: `Order` (source_id, status, created_at / paid_at / cancelled_at, currency, total,
  total_uah, customer_key), `OrderLine` (order, book, format_type paper/ebook/audio, quantity,
  price, amount_uah).
- `reports`: `DailySales` (day unique, orders, paid, cancelled, revenue_uah, items_sold,
  average order), `DailyBookSales` (day, book, format_type, quantity, revenue_uah),
  `ReportExport` (who, parameters, status, file; generated by Celery).
- Celery beat recalculates "today" every ~10 minutes and closes yesterday at night; the Redis
  cache of the report answers is invalidated after each recalculation.

Interface: Django templates + Bootstrap 5 + **Chart.js** (CDN, no frontend build), uk/en.
- Dashboard: period switch (7 / 30 / 90 days / custom), KPI tiles (revenue, orders, average
  order, paid and cancelled share, new customers), revenue line chart, top-10 books, formats
  donut, categories; every tile / chart links to its report.
- **Web reports on pages** (the user asked for on-screen reports, not only files). Every report
  page: filters kept in the URL query (bookmarkable), comparison with the previous period
  (arrow + percent), chart, sortable paginated table, buttons CSV / XLSX (the same filters,
  generated by Celery) and a print view (print CSS). Reports:
  Sales by day / week / month; Books (click -> one book page with its dynamics and formats);
  Formats; Categories; Customers (new vs returning); Cancellations.
- Orders list (as received from the events), Events journal (admins: latest events, failures),
  admin, login / logout.
- Class-based views with inheritance: `ReportBaseView` (PermissionRequiredMixin + period
  parsing + comparison + export) -> each report overrides only its query and template.
- REST: `/api/reports/summary/`, `/daily/`, `/top-books/`, `/formats/` with `?from=&to=`, JWT
  (simplejwt), drf-spectacular Swagger.
- Exports: CSV and XLSX (openpyxl).
- The sales part of A's daily email to managers moves to Analytics (an email to Analysts);
  the low-stock part stays in A.

## Stages

   groups are made by a post_migrate receiver (users/groups.py, not a data migration);
   permissions `users.view_analytics` (Analysts) and `users.use_reports_api` (Services) on

   Docker Hub push from main (coverage badge at stage 6); the external network of A is added
   at stage 2 together with the consumer.
2. RabbitMQ + B consumer (event journal, idempotency, dead-letter queue). Code written
   2026-11-18: contract in docs/events.md (version 1, full order snapshot in every event);
   apps events / catalog / sales (facts stored already at stage 2); kombu ConsumerMixin
   (events/consumer.py), quorum queue with x-delivery-limit 5, classic dead letter queue,
   database outage = wait and retry the same message; commands consume_events,
   publish_test_event, replay_dead_letters; compose service `consumer` joins external
   network bookstore_net; entrypoint runs migrate only for gunicorn. CUSTOMER_KEY_SALT is
   known only to A. A's part (rabbitmq service + network name bookstore_net) is a separate
   task in A's session.
3. A: outbox + Celery publisher with publisher confirms (in A's repository).
4. B: aggregation, reports, dashboard, exports, REST + Swagger. Sub-steps: 4.1 aggregation +
   Celery + cache, 4.2 web reports + dashboard, 4.3 CSV / XLSX exports, 4.4 REST + Swagger,
   4.5 daily email to Analysts + i18n + tests. Decisions (user, 2026-11-19, all as recommended):
   a report day = a calendar day in Europe/Kyiv (REPORTS_TIME_ZONE, reports/days.py; the
   database stays UTC); an order counts on the day it was CREATED, its payment and
   cancellation too; revenue = orders not cancelled, paid revenue is its own column;
   changed days are recalculated through `reports.DirtyDay` marks written in the event's
   transaction (a database table instead of the planned Redis set: atomic with the change,
   no Redis in tests), beat `refresh_reports` every 10 min = marks + today, `close_yesterday`
   at 01:00 UTC; cache of answers = version key `reports:version` bumped after every
   recalculation (reports/cache.py); export files stored in the database (BinaryField with a
   size limit: Railway web and worker share no disk); categories: a book counts in each of
   its categories, a note under the table says the sum exceeds the total.
   4.1 code written 2026-11-19 (reports/models.py, aggregation.py, cache.py, tasks.py,
   command rebuild_reports), committed. 4.2 code written 2026-11-19: reports/periods.py
   (?period=7|30|90 or ?from=&to=, max 366 days, previous period of the same length),
   reports/queries.py (plain data, reused by exports and REST), reports/views.py
   (ReportBaseView: Column / Tile dataclasses, sort + pagination over cached rows, ?print=1 =
   all rows + print dialog; cache keys hold real dates, not "period=30"), templatetags
   report_tags (format_value, report_cell, kyiv), Chart.js 4.6.1 via static/js/reports.js;
   events journal needs events.view_event (superusers), not Analysts.
5. A: analytics page via B's REST + backfill; integration tests on both sides.
6. CI/CD, Railway deploy, README with the architecture diagram, Swagger.

## Facts about the bookstore (A) that B depends on

  broker), sentry-sdk 2.74.0, psycopg 3.3.8, gunicorn 26.2.0 + uvicorn worker, whitenoise
  6.12.0, Python 3.13 (Docker python:3.13-slim), PostgreSQL 17-alpine with ICU uk-UA, Redis 8.

  categories (many-to-many through BookCategory), cover. `books.BookFormat`: format_type

  top books, low stock CSV attachments to the Managers group).
- A's ports on the Mac: nginx :8000, runserver :8001, PostgreSQL :5432, Redis :6379,
  Flower :5555. B uses other host ports (confirmed): nginx :8010, runserver :8011,

## Conventions (same as in the bookstore)

- black (line-length 100, target py313) + flake8 (max-line-length 100, extend-ignore E203,
  E701, E704; migrations E501 ignored) + pre-commit; CI runs both and fails on any finding.
- pytest + pytest-django + pytest-cov (`--cov-fail-under=70`), factory-boy, tests in
  `tests/unit` and `tests/integration`, settings `config.settings.test`.
- Comments explain *why*, in plain English, no abbreviations (write ManyToMany, not M2M).
- Every user-facing string translated (uk + en .po filled and compiled).
- Docker: code is COPY'd into the image (no bind mount), production settings in the image.
